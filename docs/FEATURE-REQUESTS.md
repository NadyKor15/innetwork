# Feature requests (Devpost field "[Optional] Feature Requests")

Each request: what we'd want, why it matters to InNetwork, priority (Critical / Important / Nice-to-have), and the evidence behind it. Dates UTC.

| # | Request | Why it matters | Priority | Evidence |
|---|---|---|---|---|
| FR1 | A health-care category in Alexa+ booking (a Local Booking SPI profile for clinics and practitioners, with "plan / network" and "patient age group" as first-class booking fields) | Today the documented booking path covers salons, spas and fitness; a clinic has to go through the generic MCP toolkit, and nothing in the booking contract carries the plan or the patient's age, so every add-on re-invents the network and age checks | Important | Local Booking SPI page ("Last updated: Jul 21, 2026"): "salons, spas, fitness centers, and other appointment-based services"; health/medical/doctor/clinic/insurance: 0 mentions (control: "salon" found). Integration-approach page (Jul 10, 2026): no health category |
| FR2 | A structured patient-age field in FHIR Plan-Net (e.g. `newpatients.ageRange` as a Range, not free text) | The single reason families find out on the phone that "we don't see children under 3": the directory has nowhere standard to say it. `characteristics` is a free string | Important (for CMS / HL7 Da Vinci PDEX Plan-Net; we file it here because Alexa+ add-ons would consume it) | Plan-Net STU 1.2 `newpatients.characteristics` is `string`; `npm run audit:directories` → 0 of 10,075 records state a patient age (2026-10-13, six directories; an earlier run of 2026-10-11 found 0 of 8,506 in five) |
| FR3 | Clear policy guidance for a parent-directed health navigator (an adult managing appointments for their children) | Add-on policy §4 says "must never target children or collect their data", §13 covers health content; a navigator addressed to the parent that receives a child's age band for one search is not clearly covered either way. We minimized (age band per request, never stored, verified) and simulated | Important | `policy-requirements.html` (Jul 21, 2026) §3, §4, §13; our design: SPEC N4, verify G1, mutation M-N4 |
| FR4 | Document what `hostContext.theme` carries and pass the host's type and color tokens | The design guide asks add-ons to "support light and dark mode natively" and to adapt to Alexa, but the host context's `theme` value format and any color/type tokens are not documented, so every add-on guesses | Nice-to-have | Visual Foundations + Layout and Rendering pages (Jul 21, 2026); MCP Apps `hostContext` list in the guide has `theme` without a value spec |
| FR5 | A public sandbox or simulator for Alexa+ add-ons outside the partner preview | Without it, hackathon builders reimplement a host (MCP client + MCP Apps bridge + device frame) to show their add-on; a shared simulator would make demos comparable and closer to the real device | Important | Form/forum: "the Alexa+ Add-on toolkit and web simulator are in preview with select partners" (forum thread 45397) |
| FR6 | Document directory rate limits and expose `/metadata` on every Plan-Net gateway (for CMS and insurers; Alexa+ add-ons consume these) | A health add-on cannot be reliable when a directory silently stops for the day (Molina, HTTP 403 until 00:00 UTC) or hides its search parameters (Florida Blue) | Important | friction log F1, F6b |
